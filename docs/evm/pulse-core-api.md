# Pulse Core V1: frozen calculation specification

Status: Task 1 specification frozen and Task 2 core implementation complete locally. Version **1.0.0**. The engine has been deployed and tested on Hardhat's local EVM; public release remains a later task.

Task 5B completed the [numerical/security review and release build freeze](pulse-core-review.md). The semantics and core source remain unchanged; current validation is 223 tests under both compiler profiles. The [reviewed manifest](../../evm/releases/pulse-core-v1/manifest.json) pins the exact bytecode for Task 6.

This is the normative calculation contract for Approach B: one public, immutable, stateless core, called by independent applications. All configuration and curve state are supplied as arguments. The core stores nothing, transfers nothing, emits no sale events, and does not authenticate an auction's history.

The ABI snapshot is a versioned specification fixture, not regenerated by tests. The same vectors now run against deployed local bytecode as well as the model.

| Function | Result | Meaning |
| --- | --- | --- |
| `initialize(Config,uint64 startTime)` | `State initialState` | Calculate epoch 0 |
| `quote(Config,State,uint64 timestamp)` | `uint256 ask` | Calculate the current curve's ask |
| `advance(Config,State,uint64 timestamp)` | `uint256 ask, State nextState` | Calculate one hypothetical sale and the following curve |
| `version()` | `bytes32 versionId` | `keccak256(bytes("pulse-core/1.0.0"))` |

All four functions are `external pure`. They accept no ETH. There is no constructor configuration, owner, registration, storage, external callback, payable fallback, or delegatecall in the core. A normal typed Solidity call uses the pure interface; applications need only this interface/types, not the calculation implementation. A wallet or frontend can supply inputs directly through `eth_call`.

Tuple **order**, types, names, output order, errors and semantics are frozen together:

```solidity
struct Config {
    uint256 k;
    uint256 genesisPrice;
    uint256 genesisFloor;
    uint256 pts;
}
struct State {
    uint64 epochIndex;
    uint64 openTime;
    uint64 curveStartTime;
    uint64 anchorTime;
    uint256 floorPrice;
}
```

Prices use raw payment units, such as wei or ERC20 base units. Time uses integer seconds. `k` has units of price × seconds; `pts` has units of price / second. There is no WAD scaling, decimal conversion, or fractional timestamp. The boundary clamp described below uses a one-second denominator numerically.

`genesisPrice` is an **anchor target**, not a promise of an exact opening quote. Configuration is frozen by each application for its auction lifetime. Currency, treasury, recipients, block restrictions, initialization flags and issuance data are application concerns and are absent from these tuples.

## 2. Accepted numerical domain

Let `U64 = 2^64 - 1`, `U128 = 2^128 - 1`, and `U256 = 2^256 - 1`. Inputs must first fit their ABI widths. Every division below is nonnegative integer division, rounded down. There is no wrapping or saturation.

### Configuration, checked in this order

1. `k > 0`; otherwise `InvalidCurveK()`.
2. `genesisPrice > genesisFloor`; otherwise `InvalidGenesisPrices()`.
3. `genesisPrice - genesisFloor <= k`; otherwise `GenesisGapExceedsK()`.
4. `0 < pts <= U128`; otherwise `InvalidPts()`.
5. `floor(k / pts) <= U64`; otherwise `TimeScaleOutOfRange()`.

All calculation entrypoints validate the complete configuration, including fields not directly used in a particular epoch's price calculation.

### Launch domain

After configuration validation, calculate with full `uint256` precision:

```text
initialDistance    = floor(k / (genesisPrice - genesisFloor))
transitionDistance = floor(k / pts)
minimumExclusive   = max(initialDistance, transitionDistance)
```

Require `startTime > minimumExclusive`; otherwise return `StartTimeTooEarly(startTime, minimumExclusive)`. For `quote` and `advance`, `startTime` means `state.openTime`. Do not narrow an offset to `uint64` before this comparison. If `minimumExclusive >= U64`, there is no valid `uint64` launch time for that configuration, even if the five configuration checks passed.

These checks make the initial anchor strictly positive. They also guarantee every subsequent anchor calculation at an accepted timestamp is safe: `premium >= pts`, so `floor(k / premium) <= transitionDistance < openTime <= timestamp`.

Build epoch 0 as defined in section 3 and require its opening quote to fit `uint256`; otherwise `PriceOverflow()`. This initial opening check also applies when validating a later supplied state. A valid config/open-time pair always describes a representable initial curve.

### Supplied state domain

After launch validation, require:

- `curveStartTime >= openTime`.
- `0 < anchorTime <= curveStartTime`.
- `floorPrice >= genesisFloor`.
- If `epochIndex == 0`, `curveStartTime`, `anchorTime` and `floorPrice` exactly match initialization for this config/open time.

Any failure returns `InvalidState()`. Next, evaluate the supplied state's price at `curveStartTime` and require it to fit `uint256`; otherwise `PriceOverflow()`. This rule rejects a state with an overflowing opening quote even if a much later quote would fit.

For `epochIndex > 0`, no exact relationship between epoch number, anchor offset and prior sales is required beyond the checks above. A mathematically valid snapshot is not proof of a reachable or authentic sale history. Applications supply their own canonical stored state. `epochIndex == U64` is valid for quotes but terminal for advancement.

## 3. Algorithms

### Shared price rule

Given an already validated config/state and effective time `t`:

```text
increment = k                              if t <= anchorTime
increment = floor(k / (t - anchorTime))     otherwise
ask       = floorPrice + increment
```

If `increment > U256 - floorPrice`, return `PriceOverflow()`. A zero increment, zero floor, and zero ask are all permitted; applications decide their own commercial settings. On a valid current curve, asks are non-increasing with time and never below its floor. Because a valid state's opening quote fits, its later quotes also fit.

### initialize(config, startTime)

Validate config and launch domain, then return:

```text
epochIndex     = 0
openTime       = startTime
curveStartTime = startTime
anchorTime     = startTime - initialDistance
floorPrice     = genesisFloor
```

The core can initialize repeatedly at historical or future times. It does not inspect `block.timestamp`, activate an application, reserve a launch, or enforce one-time use.

### quote(config, state, timestamp)

1. Validate config, launch and supplied state as specified above.
2. If `epochIndex == 0`, set `t = max(timestamp, openTime)`.
3. Otherwise require `timestamp >= curveStartTime`, returning `TimestampBeforeEpoch(timestamp, curveStartTime)` on failure; set `t = timestamp`.
4. Return the shared price rule at `t`.

Epoch-0 pre-open quotes, including timestamp zero, are pinned to the opening ask. A later state cannot quote an earlier epoch; use that earlier epoch's snapshot instead. There is no wall-clock lookup in this function.

### advance(config, state, timestamp)

1. Validate config, launch and supplied state once.
2. Require `timestamp >= curveStartTime`, otherwise `TimestampBeforeEpoch(timestamp, curveStartTime)`. This includes rejecting pre-open advances in epoch 0.
3. Require `epochIndex < U64`, otherwise `EpochOverflow()`.
4. Calculate `ask` using the shared price rule at `timestamp`.
5. Calculate `elapsed = timestamp - curveStartTime` and `premium = max(elapsed, 1) * pts`.
6. Require `ask + premium <= U256`, otherwise `TargetPriceOverflow()`.
7. Calculate `nextState` below and require its opening quote at `timestamp` to fit, otherwise `PriceOverflow()`.
8. Return `(ask, nextState)`.

```text
nextState.epochIndex     = state.epochIndex + 1
nextState.openTime       = state.openTime
nextState.curveStartTime = timestamp
nextState.anchorTime     = timestamp - floor(k / premium)
nextState.floorPrice     = ask
```

Step 6 is mandatory even though the next anchor can be calculated without materializing `ask + premium`. Omitting it changes the existing rejection domain. An implementation may use a checked bound comparison instead of performing the addition.

The premium multiplication fits: elapsed is at most `U64`, `pts` is at most `U128`, and their product is less than `2^192`. The minimum elapsed rule covers zero elapsed time. Consequently a separate premium-overflow error is unnecessary under this ABI/domain.

Same-timestamp transitions are allowed mathematically, including repeated simulations. The application enforces at most one successful purchase per block. The return value is a proposed state, not a persisted sale. If payment or delivery fails, the application's transaction must revert all effects.

## 4. Errors and precedence

For ABI-valid inputs, domain failures use these custom errors; they must not depend on incidental arithmetic `Panic` behavior.

| Error | Trigger |
| --- | --- |
| `InvalidCurveK()` | `k == 0` |
| `InvalidGenesisPrices()` | Target is not above genesis floor |
| `GenesisGapExceedsK()` | Initial target gap exceeds `k` |
| `InvalidPts()` | `pts == 0` or `pts > U128` |
| `TimeScaleOutOfRange()` | `floor(k / pts) > U64` |
| `StartTimeTooEarly(uint64 startTime,uint256 minimumExclusive)` | Launch time does not strictly exceed both offsets |
| `InvalidState()` | Supplied state fails structural or epoch-0 identity checks |
| `TimestampBeforeEpoch(uint64 timestamp,uint64 curveStartTime)` | Requested time predates the current epoch, except pinned epoch-0 quotes |
| `PriceOverflow()` | Initial, supplied-current, or proposed-next opening quote cannot fit `uint256` |
| `TargetPriceOverflow()` | Transition target `ask + premium` cannot fit `uint256` |
| `EpochOverflow()` | An advance would exceed `U64` |

Validation precedence is normative. If several faults coexist, return the first one in this sequence:

1. Configuration checks in section 2 order.
2. Launch-time bound, then initial opening quote representability.
3. Supplied-state shape, then current opening quote representability (quote/advance only).
4. Requested timestamp rule.
5. Epoch bound (advance only).
6. Transition target addition bound, then next opening quote bound (advance only).

After state validation, the requested current ask cannot overflow at an accepted time. It is nevertheless calculated with checked arithmetic. Solidity checked arithmetic remains a defensive implementation measure; an unexpected arithmetic panic on typed inputs is an implementation defect, not another documented domain error.

Malformed calldata, integers that do not fit ABI widths, an unknown selector or nonzero attached ETH are outside this domain-error contract. Their transport/compiler rejection bytes are not promised by this specification. The reference JavaScript model throws `TypeError` for values outside the typed ABI domain.

## 5. Rounding and compatibility

Preserve the existing division order. Deriving an anchor and then evaluating a price is two integer divisions, not an exact inverse. For example:

| Case | Inputs | Required result |
| --- | --- | --- |
| Uneven initial division | `k=10, genesisPrice=106, genesisFloor=100, pts=1, start=100` | Initial anchor `99`, opening ask **110**, not target 106 |
| Uneven transition division | `k=10, genesisPrice=105, genesisFloor=100, pts=6, start=100`; advance at 100 | Sale ask 105, premium 6, next anchor 99, next opening ask **115**, not target 111 |
| Premium equals k | `k=600, genesisPrice=1000, genesisFloor=900, pts=1, start=1000`; advance at 1600 | Sale ask 900, premium 600, next anchor 1599, next opening ask 1500 |
| Premium exceeds k | Same config; advance at 1601 | Sale ask 900, premium 601, next anchor 1601; quotes at 1601 and 1602 are both **1500**, not target 1501 |
| Zero elapsed | Same config; advance at 1000 | Sale ask 1000, premium 1, next anchor 400, next opening ask 1001 |

The actual opening increment can be materially different from the intended premium; do not describe these effects as always small. When `premium <= k`, the anchor is before the start and integer rounding can raise the increment above premium. When `premium > k`, anchor equals start and the clamp gives increment `k`.

| Compared with current `PulseAuction.sol` | V1 decision |
| --- | --- |
| Successful shared-domain calculations | Identical initialization, price and next-state arithmetic |
| Start safe for initial anchor but unsafe for minimum transition premium | Reject at initialization using `startTime > k / pts` |
| Initial rounded quote overflows | Reject at initialization |
| `ask + premium` overflows | Preserve rejection, use `TargetPriceOverflow()` |
| Proposed next state's rounded opening quote overflows | Reject the transition before returning that state |
| Epoch increment overflows | Reject with `EpochOverflow()` |
| Arbitrary caller-supplied snapshots | Validate numerical shape; no authentication or history proof |
| Existing auction string errors and arithmetic panic selectors | Not reused; the new public API has explicit custom errors and precedence |

These are intentional domain/error changes, not claims of a behavior-neutral extraction. The existing auction contract and ABI remain unchanged. Deployed-engine differential tests compare results only where both versions admit the operation; separate vectors test the stricter rejection.

### Guarantees and finite limits

- Successful `initialize` returns a state accepted by `quote`, including its opening quote.
- Successful `advance` returns `ask == quote(config, oldState, timestamp)` and a next state accepted by `quote` at that timestamp.
- Each successful transition increments epoch once, preserves open time, sets next floor to the executed ask and next start to the transition time.
- These guarantees do **not** promise that the first or every future advance succeeds. Remaining price headroom and the epoch limit are finite.

Concrete limit: `k=1, pts=2, genesisFloor=U256-1, genesisPrice=U256, startTime=100` initializes and quotes successfully, but an immediate advance rejects `ask + premium`. Apps must validate their chosen config and simulate the first purchase before opening or beginning a conditional allocation. This preflight addresses launch errors, not unlimited future liveness. Never silently clamp accumulated prices to avoid a defined failure.

## 6. Frozen application integration requirements

These rules constrain the reference consumers and later integrations; they are not extra functions or storage in the core.

| Concern | V1 application requirement |
| --- | --- |
| Engine identity | Pin an approved immutable address; verify chain/address/runtime code hash using release artifacts. `version()` alone does not authenticate code. |
| Canonical inputs | Read frozen config and live state from application storage, current time/block from the chain; validate narrowing conversions. |
| Initialization | Enforce once per application. Scheduled starts must not be in the past when accepted. |
| Scheduled pre-open reads | Return the initialized opening quote; purchases remain closed until open time. |
| Conditional pre-initialization reads | Expose `initialized=false`; price reads revert explicitly instead of presenting zero as a live quote. |
| Successful purchase | Call `advance` once, honor `ask <= maxPrice`, validate payment, commit next state and issuance reservations before callbacks, settle and deliver atomically. |
| Block limit | One successful Pulse purchase per application per block, independently for two apps sharing the core. |
| Failed settlement/delivery | Revert state, balances, reservations, nonces and events together. |
| Sale events | App emits stable `price`, `timestamp`, `nextAnchorA`, `nextFloorB`, `epochIndex` semantics; `epochIndex` is the **new** epoch, so the first epoch-0 sale emits 1. |
| Event reconstruction | App exposes config/state and opening context. Retain original deployment time separately if required by an existing launch event. |

ETH applications accept at least the ask, pay treasury exactly the ask and refund the surplus. ERC20 applications accept zero ETH and transfer exactly the nominal ask with safe token handling. The core never receives the purchase payment. Application tests must cover rollback and callback reentry across every route sharing lifecycle/issuance state.

For signatures.gallery, fulfillment of slot 1,024 atomically initializes epoch 0 at that fulfillment's timestamp. It is not a Pulse sale and does not increment the epoch. Its initial-allocation count is separate from Pulse state. Core code contains no 1,024 constant, signature check, NFT assumption or token-ID policy.

Reference integration defaults are: pausing purchases leaves the curve clock running; a later transaction in the activation block may make the first Pulse purchase. These remain proposed product choices until accepted in each application's integration specification. Exact slot fulfillment semantics, initial-phase fees, post-activation eligibility, PATH launch policy, live payment asset/chain/treasury/config and application migration policy remain application decisions. They do not block the core implementation. See [the full plan](shared-pulse-core-plan.md#14-application-decisions-still-to-record).

## 7. Implementation and verification

Task 1 freezes the interface, error precedence, domain, arithmetic, version identifier, literal vectors and integration boundaries. Specification tests compile the interface, compare its ABI/selectors with the snapshot, exercise vectors, and compare common-domain results with the existing independent curve model. They do not deploy a new engine.
